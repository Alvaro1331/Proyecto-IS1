1. Diagnóstico y Corrección en IntelliJ IDEA

Al intentar arrancar la aplicación por primera vez pulsando el botón verde de Play en TallerApplication.java, IntelliJ IDEA mostraba el mensaje de error: "The file in the editor is not runnable (Mayús+F10)".

Causa del problema:

  • El proyecto abierto en IntelliJ era la carpeta raíz del repositorio (Proyecto-IS1), la cual contiene dos subcarpetas independientes: backend y frontend.
  • IntelliJ no había detectado automáticamente el archivo backend/pom.xml como raíz de un módulo Maven, tratando los archivos Java como texto simple sin compilar y sin reconocer el método main como ejecutable.

Cambios aplicados y solución:

  1. Se configuró el archivo .idea/misc.xml vinculando explícitamente backend/pom.xml a través del componente MavenProjectsManager y asignando el JDK 17 correspondiente.
  2. Se creó la configuración del compilador en .idea/compiler.xml para el procesamiento de anotaciones de Spring Boot.
  3. Se generó la configuración de ejecución en .idea/runConfigurations/TallerApplication.xml, permitiendo a IntelliJ habilitar de forma directa el botón de Play para la clase principal.

4. Guía Didáctica: Pruebas Unitarias y Pruebas de Seguridad en Software

Definición Clave: Una prueba unitaria es un bloque de código automatizado que evalúa el comportamiento de la unidad lógica más pequeña e indivisible de un sistema (habitualmente una función o método de una clase) de forma completamente aislada del resto de la aplicación, de la red y de la base de datos física.

4.1. ¿Por qué son vitales las Pruebas Unitarias de Seguridad?

En ingeniería de software moderna, la seguridad no se prueba únicamente al final con escaneos de red o penetration testing; se implementa y valida en el código desde el nivel unitario (**Security by Design**). Las pruebas unitarias de seguridad permiten certificar:

  • Control de Acceso Basado en Roles (RBAC): Asegurar que un usuario autenticado con un rol técnico (ej. MECANICO) o externo (ej. CLIENTE) no pueda ejecutar operaciones reservadas a la administración o recepción (ej. abrir órdenes o facturar).
  • Protección contra Suplantación y Credenciales Huérfanas: Bloquear accesos no autorizados a registros incompletos o presenciales sin contraseña.
  • Integridad y Prevención de Fuerza Bruta en Autenticación: Validar que credenciales inexistentes, códigos no solicitados o contraseñas débiles sean rechazados de inmediato.

4.2. El Patrón Universal de Diseño: AAA (Arrange - Act - Assert)

Fase del Patrón AAA ¿Qué se hace en esta fase? Ejemplo de Seguridad en MotorFlow
1. Arrange (Preparar) Se instancian los objetos, se configuran dobles simulados (Mocks) y se preparan las credenciales o roles a auditar. Usuario mecanico = new Usuario(..., Rol.MECANICO);
when(usuarioRepo.findById(2L)).thenReturn(Optional.of(mecanico));
2. Act (Actuar / Ejecutar) Se invoca el método protegido que se pretende auditar. reparacionService.crearReparacion(dto);
3. Assert (Afirmar / Verificar) Se comprueba con aserciones que el sistema detectó la infracción y lanzó la excepción de seguridad esperada. assertThrows(IllegalArgumentException.class, ...);
assertTrue(msg.contains("no tiene permisos"));

4.3. Dobles de Prueba: Aislamiento con Mocks (Mockito)

Para probar la lógica de un servicio (como UsuarioService, ClienteService o ReparacionService) sin necesidad de conectarse a MySQL ni alterar datos reales, se emplean Mocks:

  • mock(UsuarioRepository.class): Crea un repositorio virtual en memoria RAM.
  • when(repositorio.findByEmail("atacante@externo.com")).thenReturn(Optional.empty()): Simula con exactitud la respuesta del almacén ante un email inexistente.
  • ReflectionTestUtils.setField(...): Inyecta el mock dentro del servicio privado.

4.4. Catálogo de Aserciones Principales en JUnit 5

Aserción Propósito en Pruebas de Negocio y Seguridad Ejemplo
assertEquals(esperado, actual) Comprueba igualdad matemática exacta o mensajes textuales de error de seguridad. assertEquals("Contraseña incorrecta.", ex.getMessage());
assertTrue(condicion) Verifica que una condición booleana o de contención es estrictamente verdadera. assertTrue(cliente.tieneCuenta());
assertFalse(condicion) Verifica que una condición booleana es estrictamente falsa. assertFalse(presupuesto.estaCaducado());
assertNotNull(objeto) Garantiza que un código o token generado no es nulo. assertNotNull(reparacion.getLocalizador());
assertThrows(Excepcion.class, lambda) Esencial en seguridad: Verifica que una acción no autorizada detona el corte inmediato de la ejecución con una excepción. assertThrows(IllegalArgumentException.class, () -> service.crearReparacion(dto));

7. Pasos para Crear una Nueva Prueba Unitaria de Seguridad (Checklist Rápido)

  1. Identificar el vector o regla de seguridad: Determinar qué condición de autorización o validación (rol, contraseña, token) debe proteger la operación.
  2. Configurar el escenario malicioso o no autorizado (Arrange): Simular mediante Mocks al actor no permitido (ej. un usuario con rol inadecuado o credenciales inválidas).
  3. Ejecutar y atrapar el fallo (Act & Assert): Utilizar assertThrows(IllegalArgumentException.class, ...) comprobando que el método detiene la acción sin efectos colaterales.
  4. Validar el mensaje de seguridad: Comprobar con assertTrue o assertEquals que el mensaje de error es explícito y coherente con las políticas del taller.
